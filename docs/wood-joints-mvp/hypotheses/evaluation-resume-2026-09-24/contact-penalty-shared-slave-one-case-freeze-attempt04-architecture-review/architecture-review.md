## Findings

1. **Medium — Freeze hash and parse still use separate reads.** verify_freeze() hashes input-freeze.json and then separately reopens it for parsing (run.py:191-197). The verifier likewise parses the freeze and later hashes it for the authorization binding (verifier.py:1167-1189, 1238-1239). If concurrent filesystem mutation is in scope, the parsed freeze object could differ from the bytes whose digest the external authorization names. Use the shared snapshot reader for the freeze anchor in both paths. This requires concurrent mutation; no such mutation was observed.

2. **Medium — The one-run cap is resettable by deleting its local evidence.** The runner blocks when execution.json or output/ already exists (run.py:337-340), but these are the only visible replay guards and the external authorization is reusable. Removing those artifacts permits another run with the same freeze and authorization, so runs_total: 1 is enforced only while prior output remains. If this is intended as a hard per-freeze cap, make the authorization/run state one-use outside the deletable output tree; otherwise describe it as an operator-maintained limit.

The authorization record's reviewer identity remains an explicit external trust assumption, not an architecture defect. This review did not execute the candidate, its tests, Docker, or a solver; it assesses packet structure and recorded state only.
