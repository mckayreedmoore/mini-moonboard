# Current nut-coupling order and explicit-mode source feasibility

This is a read-only source review. It does not change a deck or establish a native result. The pinned A09 `response_n_plus.inp` is a `*STATIC` response input with nonzero ramped nodal loads (`WJ_RAMP` and `*CLOAD`, lines 17–29). The historical `input-freeze.json` instead says `FROZEN_ZERO_LOAD_INPUT_NOT_EXECUTED` and describes a zero-load matrix-storage tangent. That scope description conflicts with this response deck and is preserved as historical metadata, not adopted as its loading or execution provenance. This review directly hashes the actual deck and shared input bytes; the conclusions concern whether their constraint/material structure can be carried into explicit dynamics. No native explicit result is established here.

The historical controller-first six-DOF fit makes each nut REF/ROT control DOF dependent in a user `*EQUATION`. A parent source-incidence audit confirms that all 24 historical dependent DOFs are exactly the four current rigid bodies' REF/ROT DOFs; the current physical-pivot fit instead makes 24 shaft DOFs dependent and leaves those controls independent. The assembled A09 has four `*RIGID BODY` cards, with the same controls on the independent side of solver-generated rigid MPCs. In CalculiX 2.23, `rigidbodys.f` generates those MPCs through `rigidmpc.f` and labels them `RIGID`; `cascade.c` classifies `RIGID` as nonlinear and sets `icascade=2` when an independent term of a nonlinear MPC is dependent in another equation. `nonlingeo.c` then stops an explicit dynamic calculation when `icascade==2` (lines 385–389). Thus controller-first is source-disallowed for explicit dynamics with the current rigid-body cards. This conclusion follows from the dependency graph, not displacement size or material linearity. The NSET form generates node MPCs; it does not deactivate the nut elements before the stable-increment element scan.

`*RIGID BODY` itself implies nonlinear geometry (`rigidbodys.f` 58–65) and is rejected in perturbation steps. A small-motion or linear-material interpretation therefore does not turn the generated rigid MPCs into linear equations. The current physical-pivot fit instead makes shaft DOFs dependent and leaves the six rigid controls independent; its producer records an invertible row-space transformation of the same six linear fit equations. This avoids the controller/rigid-MPC mixed dependency in the explicit source path. It does not make the fit a finite-rotation thread model, and it does not establish the current model's explicit readiness.

There is an independent explicit-method blocker in the current material/mesh inputs. The four nut ELSETs contain C3D10 solids and are assigned `NUT_ZERO_MASS_RIGID_CARRIER` with density 0 and elastic modulus 200000. The four rigid-body cards constrain those solids; they do not remove their elements from the mesh. In `calcstabletimeincvol.f`, active elements are scanned without a rigid-body or zero-density exclusion (143–153); the isotropic wave-speed expression divides the elastic term by `rho` (318–322), and the stable increment is inversely proportional to that wave speed (415–419). `materialdata_me.f` returns the declared density (74–95). For this positive-modulus, zero-density C3D10 material, the source path therefore has no finite positive element stable increment under ordinary IEEE arithmetic; its mass-scaling / too-small-increment handling is at 429–485. This is a source-based warning, not an observed solver failure; runtime floating-point behavior was not tested. Reordering the nut equations cannot resolve it.

**Disposition:** do not use controller-first ordering for an explicit model that retains these rigid-body constraints. The pinned source only establishes an explicit prohibition; it does not establish whether the historical ordering would be acceptable in an implicit geometric-nonlinear run. The current physical-pivot ordering is not a validated explicit workaround because the existing carriers still have zero density and the actual port fit remains an infinitesimal-rotation construction. No new deck, native run, geometry/material change, or acceptance claim is proposed by this review.
