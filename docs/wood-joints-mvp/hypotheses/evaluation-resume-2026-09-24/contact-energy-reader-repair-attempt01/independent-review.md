# Independent source review: F2F contact-energy reader proposal

I reviewed the frozen proposal at `source-pins.json` SHA-256 `817907d382af23167e5fa46a4bf882667dd822a57f31f8454e90bd46b4d39635` and README SHA-256 `b292e3077ff3103583c3617b43d68af91a965e84dd24cb998eba482de9846d3b`. Every base, proposed source, patch, fixture, and report entry in the manifest matched its current file hash. The listed CalculiX 2.21 sources are bound to archive SHA-256 `52a20ef7216c6e2de75eae460539915640e3140ec4a2f631a9301e01eda605ad`.

The proposed sparse-address read follows the actual writer. `gencontelem_f2f.f` stores the point ID after the generated contact-element node list; `resultsmech.f` reads that ID and writes the F2F energy components to `ener(1:2,1,ne0+igauss)`. The proposed `calcenergy.f` uses the same offset only when `mortar==1` and the generated label is `ESPRNGC`; other contact and spring branches retain the existing `nelem` slot. `results.c` passes the retained base and mortar flag through the energy worker, and `CalculiX.h` matches the added arguments. The proposed `printoutelem.f` uses the same narrow gate for `CELS`/`ELSE`. This agrees with the writer/reader address mismatch observed in the pinned point map.

The mechanical scope is correctly described. At a fixed displacement and time, these edits change no contact law, load, force assembly, tangent, or Newton residual. They change the stored-energy values consumed by `calcenergy`, which populates global contact elastic/viscous energy totals used in implicit-dynamic contact control. Those totals can alter impact decisions, cutbacks, and later accepted history. The `printoutelem` change only affects reported `CELS`/`ELSE` energy. This proposal therefore needs a completed native diagnostic with the rebuilt source before it is used for response analysis; the source patch and one-state map do not validate later dynamics.

`printout.f` keeps two distinct indices. `contactenergybounds` is called once at routine entry, before the output loop: it computes the last original element as the F2F energy base and the first generated CE as the contact-loop start. The contact-output branches assign the latter to `ne0`, but pass the saved base to every `printoutelem` call. Thus a `CSTR`/`CDIS` request before `CELS` does not turn the first-CE element ID into the sparse-energy base. For `mortar==0`, the energy base remains `ne` and the reader retains compact indexing. The `printoutebhe` and C declaration plumbing passes the existing base argument; the EBHE path does not request `CELS`.

The independent calcenergy fixture compiled and ran the proposed production `calcenergy.f` with `-fcheck=all`; its sparse F2F, legacy mortar-zero, ordinary spring, and no-active-element cases all passed. The printout fixture also compiled the proposed production `printout.f` and `printoutelem.f` with bounds checking and returned zero with eight checks. Its frozen result is documented in [the parent fixture addendum](parent-printout-fixture-results-addendum.md), SHA-256 `87f8f2eb72dcaadbd7b1a738dc42b22092584fa175f43f6c6628d315ac2ffa1b`.

One integration limit remains explicit: the printout fixture calls the production `contactenergybounds` helper and `printoutelem` directly, but does not call the full `printout` routine with an ordinary contact-output request followed by `CELS`. Static source inspection confirms the helper is called before the loop and the saved base is passed at every call site; a whole-routine sequence check remains a useful combined-build validation. Neither fixture is a full CalculiX build or native joint solve. Restart continuation and later dynamic-history behavior are likewise outside this review.
