# Attempt04 architecture review

The recorded build chain, base-image lock, source additions, job-level footer placement, and disabled-capture path are internally consistent. Two integration items need resolution before relying on this packet for a native capture: the candidate-row cap is described inconsistently, and sink flush/close errors are not checked. This review does not accept runtime behavior or mechanics.

## Findings

1. **Candidate-row cap contract is ambiguous.** The contract states a 250,000-row limit across both passes, a 250,000-row pass-one limit, and an additional 250,000 rows for optional pass two (`capture-contract.json`, fields `candidate_point_rows_per_generation_across_both_passes`, `pass1_candidate_points_max_when_pass2_absent`, and `optional_pass2_additional_candidate_points_max`). The sink's `WJCC_MAX_POINTS` and `wjcc_point_append` enforce 250,000 rows total across both passes (`capture-sink.inc`, lines 19 and 205–219). If the caps are conjunctive, the combined limit controls and the additional-pass field is redundant; if “additional” means rows beyond pass one, the producer is stricter than that reading. Clarify whether the intended limit is combined or per-pass and make the contract and producer agree. This is a specification ambiguity, not a demonstrated false acceptance or rejection. The offline reader enforces byte, line, generation, and face-row ceilings, but does not independently check the candidate-row ceiling; it relies on the pinned producer for that limit.

2. **Buffered output errors are not reflected in the footer status.** `wjcc_emit` checks `fwrite`, but `ccxcap_generation_end_` ignores the result of `fflush`, and `ccxcap_finish_` ignores both `fflush` and `fclose` (`capture-sink.inc`, lines 115–121, 483, and 549–556). The footer's error and complete fields are formed before the final flush and close. A delayed output failure can therefore escape the producer's error flag. The strict reader will reject missing or truncated records in ordinary cases, but the producer's complete flag does not itself attest successful persistence. Propagate these I/O results and ensure a failed flush cannot leave a success footer.

## Lifecycle, fast path, and bounds

The patch contains one `ccxcap_finish_();` call, after the CLI step loop and `FORTRAN(closefile,())`. The sink keeps capture state across `nonlingeo` step returns, emits the terminal footer at that job boundary, then closes the stream, frees the retained arrays, clears their pointer/length pairs, and disables itself. The pending-generation guard links each begun sweep once; an early process exit leaves no valid terminal footer. These are source-placement findings, not runtime multi-step evidence.

With no capture-path environment variable, the first generation hook caches capture as disabled and returns before opening output or allocating capture buffers. `gencontelem_f2f` queries cached activity once and guards face/point calls; the post-results spring scan is also activity-guarded. The begin and iteration-link hooks still run on the contact path, and loop guards remain. The packet makes no runtime benchmark claim.

The sink bounds capture bytes at 134,217,728, record lines below 2,048 bytes, generations at 64, ties at 128, the frozen face roster at 13,001, candidate rows at 250,000 per generation across both passes, Gauss indexing at 1,000,000 slots, and state snapshots at 1,000,000 doubles. It reserves 4,096 bytes for the footer and treats allocation, write, identity, validation, or cap failures as invalid. The 1,664,128 maximum face-row count follows from 64 sweeps × two passes × 13,001 faces. The reader independently checks file bytes, line size, generation count, and face-row count; see Finding 1 for its candidate-row check boundary.
