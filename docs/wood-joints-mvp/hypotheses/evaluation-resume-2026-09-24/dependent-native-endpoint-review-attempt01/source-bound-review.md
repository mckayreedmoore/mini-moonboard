# Dependent-native endpoint and first-state review

## Finding

The upstream run’s terminal `solver_failed` status is caused by CalculiX’s end-of-step negative-contact-pressure cleanup, after an accepted first increment. It is not an initial time-step roundoff shortfall. The frozen deck has `*DYNAMIC` controls `0.0005, 0.0005, 1e-06, 0.0005`: the initial normalized increment is `dtheta = tinc/tper = 1`. The first increment converges in 23 iterations. `checkconvergence.c` then advances to the end and clamps the *next* increment to the zero remainder. With true contact and pressure ratio `-0.2665078 < -0.05`, `nonlingeo.c` appends its zero-size cleanup pass by setting `theta=1-1e-6` and `dtheta=1e-6`. At period `0.0005`, this next physical increment is `5e-10` seconds. That is why the log reports a previous-time cursor of `0.0004999995` before the cleanup pass: it was written by the explicit rewind, not by a short first increment.

The appended pass diverges after two iterations. At this retry, `checkimpacts.f` prints a maximum-allowed physical increment of `1e-6` seconds, the configured minimum. For surface-to-surface contact (`mortar==1`) on this first cutback (`icutb==0`), `checkconvergence.c` does not multiply the current `dtheta` by the cutback factor; it then compares the existing normalized `1e-6` against `tmin/tper = 0.002` and stops with “increment size smaller than minimum.” The log’s “decreased to 5e-10” line therefore does not mean a smaller attempted increment was taken. Exit 201 / `solver_failed`, with `oom_killed=false`, describes the cleanup-pass failure and must stay separate from first-state equivalence.

## First accepted state and comparison scope

The first state is eligible for the planned output-only comparison, subject to the independent comparator’s checks. Before solving increment 1, `nonlingeo.c` sets `time=(theta+dtheta)*tper=0.0005` and `dtime=dtheta*tper=0.0005`. After convergence, the negative-pressure branch changes only the next-step cursor (`negpres`, `theta`, `dtheta`); it does not change the accepted solution, `time`, or `dtime`. The immediately following output branch runs only for `icutb==0` at the requested frequency. It calls `results()` with the accepted state and those unchanged `time`/`dtime` values. In the instrumented source, the output-only hook runs after `resultsforc()` and writes `ttime+time` and `dtime`; its first state should be `(step=1, increment=1, time=0.0005, dtime=0.0005)`. This establishes the intended timestamp and state path; it does not assert that the two executables’ values match.

The upstream evidence agrees: `pilot.sta` has accepted increment 1 (23 iterations) and marks increment 2 `1U` after two iterations. `pilot.dat` contains only the `INCREMENT 1` report, including 105 per-pair report blocks for all 35 named pairs (three blocks per pair), all at `0.5000000E-03`; its pivot `RF` report is at the same time. `pilot.frd` contains six records tagged step 1/increment 1 at `5.00000E-04`, including `STRESS` and `CONTACT`; its two later records are step 1/increment 2 from the failed cleanup pass. `ResultsForLastIterations.frd` also contains only increment-2 failure records. Compare the accepted increment-1 records only; do not compare the files wholesale or include either increment-2 residual sequence.

The instrumented acquisition is now terminal too: its execution record is `solver_failed`, exit code 201, with `oom_killed=false`. Parent terminal validation records one accepted increment and confirms that `pilot.log` and `pilot.sta` are byte-identical to upstream. The hook CSV records one state at step 1/increment 1 with `time=dtime=0.0005`, 24 MPC rows, and 337 acceleration rows; parent validation confirms the exact support IDs. This establishes successful hook capture for the accepted first state, not executable equivalence. The full accepted-prefix comparison remains pending.

No fixture change is needed to obtain the first accepted state. Running the already frozen instrumented arm unchanged preserves the paired inputs and targets the same first physical time. Keep the run-level result `solver_failed` if its later cleanup pass fails, and report first-state equivalence separately. Extending the step period alone would merely move the endpoint cleanup check to a later increment; it does not provide a reliable zero-exit fix. A full-horizon or early-stop design would be a separate attempt, not a reason to edit this frozen fixture.
