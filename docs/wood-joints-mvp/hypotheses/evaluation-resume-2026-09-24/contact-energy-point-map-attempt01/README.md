# Contact energy point-map diagnostic proposal, attempt 01

This is an output-only source proposal to resolve the first-state energy discrepancy. It does not change the contact law, controller, or model. The proposed sources have not been built into a full CalculiX executable or run in a native joint solve.

The frozen first-state audit reports 35 `WJ_E_IF` values summing to `3.478603644581712e-11 N·mm`, while the `CELS` rows sum to `1.091529611754609e-9 N·mm` and the log rounds to `1.091530e-9 N·mm` (`first-state-contact-output-audit-attempt01/result.json`, SHA-256 `ae44acf254748eb0c4ee01531ff62bc9ea41a41fd2d602f9168a7494c6608b13`). Those totals disagree beyond their printed precision; this proposal collects pointwise inputs so a later audit can locate the source without inferring from aggregates.

## Source path and change

The C base is the `results.c` copied into `finite-actuator-angular-momentum-audit-attempt01/angular-output-build-attempt01/inputs/` (SHA-256 `2ce3ba3c2ab1e20da99db94585a827c3267c83586e8c0e4ad10f926c1795033a`). The Fortran base is its paired `printoutcontact.f` (SHA-256 `4cf339d0b041034279ccbd9da9724b73ee8e1848005a63cb2bc6895f348d2af6`). Both source copies and proposed copies are retained under `source/`; the two unified diffs are at `results.c.patch` and `printoutcontact.f.patch`.

The C helper is called only beside the existing `wjdep_write_output` accepted-output hook, under the same `CCX_WJ_DEP_RESIDUAL_AUDIT=1`, `iout==2`, `nmethod==4` guard. `resultsmechmt` has populated the point arrays earlier in this `results()` call. One block is written for every unique step/increment, with the expected active-contact point count in `STATE`, an `END` row that repeats that expected count, and `fflush` after the block. `END` is a function-end marker, not an independently accumulated write count. A later parser must independently count actual `POINT` records and compare that count with `STATE` and `END`; a missing `END`, partial row, or count mismatch marks a partial block. The file is `pilot.wj-contact-energy-map.csv` in the solver working directory.

The 23-column CSV has `STATE`, `POINT`, and `END` record types. Each `POINT` includes the zero-based C element slot and one-based Fortran element id, original `igauss` and `jfaces`, `springarea(1,igauss)`, `stx(1,1,nelem)` native clear, `stx(4,1,nelem)` pressure, and both elastic/viscous values at the writer index `ne0+igauss` and compact reader index `nelem`. If `nener` is not 1, the four energy values and their two energy indices are written `NA` rather than read. `energy[2]` is not included: `results.c` calculates that total only in the `iout<=0` path, whereas this hook runs for `iout==2`.

Inside the existing `CF `-only loop, the Fortran addition writes adjacent `WJ_CEP_POINT` and `WJ_CEP_VALUE` records to the `.dat` output whenever that `CF ` print request runs. These rows are intentionally unconditional with respect to the environment variable, matching the existing `WJ_ANGULAR` and `WJ_E_IF` records in this printer. The C CSV alone is gated by `CCX_WJ_DEP_RESIDUAL_AUDIT=1`; the planned joint diagnostic must enable that existing gate to get both streams. The point tag contains tie id, slave/master set names, Fortran element id, `igauss`, `jfaces`, and time. The value row contains area, native clear, pressure, the printer's reconstructed `clearproj`, and its per-point energy contribution. Those rows join the C map by element id, `igauss`, `jfaces`, and time; the C map supplies step/increment. The Fortran routine has no step/increment arguments, so the `.dat` tag intentionally does not claim them.

## Source-backed interpretation

In pinned CalculiX 2.21, `gencontelem_f2f.f` stores `nopes+nopem` in `kon(id)` and stores `igauss` and `jfaces` in the next metadata positions; `ipkon(nel)` is the generated element's one-based `id`. The C reader therefore uses `conn0=ipkon[i]-1`, reads `nope=kon[conn0]`, then reads metadata at `conn0+nope+1` and `conn0+nope+2`. `nopes=nope-nopem`; 3-, 4-, 6-, and 8-node faces are accepted. It does not subtract the four extra allocated metadata slots from the node count.

`resultsmech.f` writes current contact elastic/viscous energy to `ener(:,:,ne0+igauss)` after evaluating the contact spring. `calcenergy.f` and the `CELS` path in `printoutelem.f` read compact `ener(:,:,nelem)` slots. The point map records both exact addresses and values rather than assuming they coincide. `resultsmech.f` writes the two values only when `nener==1`. No inferred maximum `igauss` bound is added: `results()` has no `nslavs` extent argument, and these rows use the active generated point ids whose energy/spring-area slots the immediately preceding native writer just accessed.

For a linear frictionless spring, `springforc_f2f.f` computes elastic energy from the native clearance and current spring force. The existing printer instead reconstructs `clearproj` from `co+vold`; its source leaves the `clearini` term commented out, while `springforc_f2f.f` adds `clearini*reltime` to the slave point coordinates. Recording both native `stx(1)` and reconstructed `clearproj` distinguishes that possible offset from writer-versus-reader indexing. It does not assign the discrepancy to either cause.

## Checks and limits

`synthetic-point-map-check.py` passes synthetic checks for one 6+6 triangle contact and one 3+4 contact, metadata offsets, sparse writer/compact energy addresses, a nonzero `clearini*reltime` offset, and 23-column block framing. It also verifies the original `wjdep_write_output` function body is byte-identical to the pinned C base and the new helper/call appear once. The parent separately compiled the extracted C emitter in `parent-emitter-harness-attempt01`; that focused harness is not a full CalculiX build. The source contains no independent `springarea` allocation bound in `results()`; no arbitrary bound is guessed. A later run must still validate the final compiled binary/source pins and inspect completed CSV/DAT blocks before interpreting values.

The upstream source archive is pinned at SHA-256 `52a20ef7216c6e2de75eae460539915640e3140ec4a2f631a9301e01eda605ad`. The relevant source file pins are in `source-pins.json`.
